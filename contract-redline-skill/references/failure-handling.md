# 失败分流与边界处理

## 一、输入文件边界

### 1. 不是 `.docx`
直接停止，不要尝试按本 skill 修订。

建议回复方向：
- 请提供原生 `.docx` 文件
- 如果目前是 PDF、图片、扫描件、OCR 文本，需先转成可编辑的 `.docx`

### 2. `.doc` 转换来的 `.docx`
可以继续，但必须提示风险：
- 结构可能与 Word 原生 `.docx` 不一致
- 可能出现空白页、段落错位、样式异常

优先建议用户：
- 在 Microsoft Word 或 WPS 中打开一次
- 使用“另存为”重新生成 `.docx`
- 再交给本 skill 修订

### 3. 文档损坏或无法解析
直接停止。不要猜测缺失内容，不要在损坏文档上继续修订。

## 二、业务信息不足

下列信息缺失时，应先追问：
- 代表哪一方
- 市场地位
- 修订重点或特别关注条款

如果用户只说“帮我改合同”，不能直接开始 apply。

输出方式不必默认追问。脚本采用事务式原地修订：临时工作副本全部通过后才替换原文件，失败时原文件不变。只有用户明确要求另存修订稿时才设置 `output`。

## 三、执行边界

### 1. 不适合自动精修的场景
下列情况应谨慎，必要时停下说明：
- 需要整份合同重写
- 需要跨多个段落重构逻辑顺序
- 需要整体排版重做
- 需要大规模统一替换但定位点不清晰

### 2. 复杂对象风险
以下对象可能超出安全自动修订范围，应提示用户：
- 表格中的复杂嵌套内容
- 页眉页脚
- 文本框 / 形状内文字
- 自动目录 / 域
- 批量编号联动段落

可行时优先：
- 先 inspect 结构
- 根据 `risk_flags`、段落 `container` 和 `safe_for_text_redline` 判断是否适合自动修改
- 能做小改则做小改
- 无法稳定落地则加 comment 或说明未处理

说明：
- 本 skill 默认不要求本机启动 Microsoft Word
- 但对复杂对象的最终视觉核验，仍建议在 Word 或 WPS 中人工打开检查

## 四、处理方式选择规则

- 可在一个安全block内闭环表达的修改选择 `edit`，并给出完整终稿；渲染器负责最小差异。
- 需要提示用户、确认商业参数或不适合自动改正文的事项选择 `comment`。
- 跨block重构、混合格式、复杂对象或无稳定锚点的事项转为人工处理。
- LLM不得选择或手写 `replace_text`、`delete_text`、`insert_before`、`insert_after`、`replace_paragraph`、occurrence或字符位置。

### 不应自动修改的内容
- 空白日期、空白金额、签字页信息
- `【  】`、`____`、留空表格单元格等占位内容
- 需要用户自行确认的商业数字、比例、费率、期限或主体信息
- 未结合交易标的金额、风险大小、履行难度和谈判空间评估，就上调违约金金额/比例、压缩履行期限、拉长己方期限等交易参数调整

## 五、已有修订的处理

如果文档已包含他人修订：
- 原则上允许继续追加修订
- 不要擅自接受或拒绝他人修订
- 继续追加时，要保留原有修订并续增新的 revision id

如果已有修订导致结构异常、文本无法定位：
- 不要硬改
- 说明该段无法安全自动处理
- 视情况转为 comment 或要求用户提供更干净的版本

如果目标文字本身位于已有修订、超链接、域、文本框或其他复杂对象内部，脚本应拒绝修改，而不是拆坏原有 OOXML 结构。

## 六、半成品修改不得提交

以下情形属于未完成的半成品修改，不应直接 apply 成交付稿：
- 只删除风险词，但未补足保护结构
- 只把条款语气改软，但未修复责任分配或权利边界
- 改后无法明确说明“谁在什么条件下承担什么责任”
- 同一风险点需要联动修改多处才能成立，但当前只改了其中一处
- 删改后造成句义悬空、条件断裂、责任失衡或程序缺口

遇到上述情况时，应按以下顺序分流：
1. 优先补句、补前提、补例外、补责任边界，做到当前句或当前款内闭环
2. 如小粒度动作无法改到位，升级为局部重写
3. 如仍无法稳定落地，改为 `add_comment`
4. 在最终输出中明确标记该处未安全自动处理

执行层必须使用临时工作副本承载全部 operation。任一 operation、增量校验或结构校验失败时，删除临时文件，不得把已经写入部分修订的文件覆盖回原文件。

## 七、稳定锚点、依赖组与技术失败

- 所有正文修改和批注必须绑定当前 snapshot 的 `block_id`、完整block原文及其哈希。
- 锚点不一致时返回 `BLOCK_ANCHOR_MISMATCH`；不得在全文模糊搜索、猜测新段落或沿用旧轮次锚点。
- 法律上必须共同成立的修改归入同一 `dependency_group`。一项失败时整组退出，不允许只交付半个法律方案。
- 无关依赖组独立预检；某组技术失败不得自动拖垮其他组。
- 定位、offset、XML、格式或渲染错误属于程序问题。不得让LLM通过缩短、弱化或改变拟议法律文本来迁就技术限制。
- 若某风险从一开始就不适合正文自动修改，应在intent阶段选择批注；技术失败后新增批注方案需要重新进行法律判断，不是底层自动替换。
- 评测或调试时，把intent、编译计划、分组结果和结构化错误保存到受控证据目录；合同目录仍保持干净。

## 八、输出边界

本 skill 的目标是交付修订稿，而不是输出长篇审查意见。

因此不要：
- 生成“合同审查意见.md”
- 生成“修订建议.md”
- 长篇展开推理过程

只需要输出：
- 已更新的原文件路径；用户明确要求另存时才输出另存路径
- verify 结果
- 操作摘要
- 未处理风险点

任务完成后不要在合同目录留下 `ops.json`、临时 DOCX、备份 DOCX 或额外修订稿副本。
