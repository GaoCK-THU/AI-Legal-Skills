# 合同修订判断框架

本文件承载“合同为什么要改、优先改什么”的业务判断规则。

## 一、双重视角

修订前，先同时从两个视角看条款：

### 1. 正常交易视角
关注合同在正常履行状态下是否可执行：
- 谁负有义务
- 在什么时间履行
- 要达到什么标准
- 付款、交付、验收、保密、知识产权安排是否清楚

### 2. 应急安排视角
关注出问题时能否保护委托方：
- 违约后果是否明确
- 救济措施是否足够
- 解除、终止、追责、争议解决是否可落地

## 二、条款定性三问法

每个拟修订条款，都先回答三问：

1. 这个条款约束的是谁？
2. 它对委托方的影响是保护、限制还是中性？
3. 你准备做的修改，是否真的让委托方更有利？

如果第三问无法明确回答，就不要直接改文档。

## 三、重点扫描顺序

按以下顺序优先扫描：

### 1. 鉴于 / 背景 / 权利来源
- 是否存在“唯一拥有”“排他”等过度承诺
- 是否需要补“或经合法授权”“或授权使用人”等兜底表达

### 2. 核心权利义务
- 己方是否承担了过重、过细、难执行的义务
- 对方义务是否过于抽象、缺少时间和标准

### 3. 付款 / 结算 / 验收
- 付款条件是否过于前置
- 验收标准是否不清
- 默认确认、自动验收条款是否过度压缩己方权利保护期

### 4. 违约责任
- 己方责任是否无上限或明显过高
- 对方责任是否模糊、难执行
- 是否出现“全部损失”“连带责任”等过重措辞

### 5. 解除 / 终止 / 争议解决
- 己方是否缺少退出机制
- 管辖、仲裁地是否明显不利
- 通知、送达、补救期限是否合理

## 四、常见误判

### 1. 义务期与权利保护期混淆
例如“甲方应在15日内确认”，表面看是甲方要行动，实质上也是甲方的审核和异议保护期。对委托方有利的确认期，不应随意缩短。

### 2. 双向条款只看单边
例如“违约方赔偿损失，最高不超过合同总金额”，如果双方都适用，限制的可能不只是己方责任，也限制了己方可获得的赔偿。

### 3. 过度追求全面修改
不是所有风险都要改进正文。对于暂时无法安全自动化替换、但需要提醒用户的事项，优先考虑批注而不是粗暴重写。

过度修订同样是质量问题。下列内容原则上不改正文：
- 只属于语言风格、行文顺序或表达偏好的优化
- 原条款虽不完美，但不会实质影响委托方核心利益或合同履行
- 修改后只是更强硬，却不一定更可执行
- 为了覆盖所有风险而加入与本交易关系不大的兜底条款

### 4. 把交易参数当作法律修订
金额、比例、费率、违约金标准、履行期限、通知期限、补救期限、付款周期等，通常兼具法律后果和商业谈判属性。它们不是绝对不能改，但必须先判断必要性，不能把“更有利”直接等同于“应修改”。

交易参数修改前，至少综合评估：
- 交易标的金额、合同总价、付款规模或单次订单金额
- 违约可能造成的损失范围、替代履行成本、维权成本和时间成本
- 违约发生概率、履行难度、时效敏感性和行业习惯
- 原金额、比例、费率或期限与风险敞口是否匹配
- 委托方市场地位、谈判空间和对方接受可能性
- 是否存在前后不一致、计算错误、明显笔误、强制性规定或可执行性问题

下列修改不能仅凭立场直接进正文：
- 仅因代表守约方或强势方，把违约金金额上调，例如 `5000元` 改为 `10000元`
- 仅因希望加重责任，把违约金比例上调，例如 `20%` 改为 `30%`
- 仅因希望压实对方义务，把履行期限压缩，例如 `8小时` 改为 `4小时`
- 仅因希望己方更从容，把期限、账期、宽限期机械拉长

如果结合交易标的金额和风险大小可以说明原参数明显不足或明显过重，可以直接红线调整；否则只加批注提示用户确认商业口径，不用红线直接改数字。调整正文时，摘要中必须说明该参数为什么需要改，而不是只写“更有利于委托方”。

## 五、按市场地位调整修订力度

### 强势方
- 更积极压实对方义务
- 在确有必要且不属于擅自调整商业参数时，适当延长己方履行期限或确认期限；金额、比例、费率、违约金和期限调整仍须先通过交易参数必要性判断
- 要求更明确的违约责任和退出机制

### 平等方
- 追求义务对等、责任对等、程序对等
- 优先修明显失衡或不可执行条款

### 弱势方
- 优先保核心：付款、责任、解除、争议解决
- 不追求面面俱到，优先把高风险点改到可接受

## 六、处理方式选择原则

LLM只选择高层处理方式：

1. `edit`：提供该block修改完成后的完整文本。
2. `comment`：保留正文，对连续原文添加批注。
3. `manual`：跨block重构、复杂对象或无可靠锚点时由人工处理。

补充规则：
- `edit`仍应遵循最小必要修改，但由渲染器比较完整原文与完整终稿并一次性生成tracked changes；LLM不拆底层operation。
- 能在当前block内补足保护结构，就不要跨block重构。
- 能不改正文而不影响委托方实质利益，就不要为了完整性或风格统一而改
- 不能只删除“唯一”“全部”“无条件”“任何”“自动”“不可撤销”等风险词，而不补足替代表述、限定条件、例外或责任边界
- 优先补限定条件、例外、前提、责任边界，再考虑纯删除；如果纯删除会让条款保护变成半截，就不算合格修改
- 无法安全自动落地的判断，在intent阶段优先选择 `comment`
- 每一处修改都应能用一句话说明目的，例如：
  - 明确付款前提
  - 延长己方确认期
  - 限制己方赔偿上限
  - 细化对方违约责任
- 不修改空白填写项，例如空白日期、空白金额、`【  】` 等占位内容
- 文档已有他人修订时，只追加新修订，不接受或拒绝原有修订

## 七、同句/同款闭环检查

每一处修改完成后，必须立刻检查该句或该款是否已经形成完整保护闭环，至少确认以下问题：
1. 义务主体是谁
2. 触发条件是否清楚
3. 时间或期限是否清楚
4. 履行标准或责任范围是否清楚
5. 例外、前提或补救程序是否补齐
6. 违约后果或救济是否仍然可落地

如果某次修改只是把条款语气改软，但没有解决责任分配、条件触发或程序前提问题，则该修改不视为“精修到位”。如果删词后导致句义悬空、责任失衡、条件断裂或保护不足，必须同步补句、补前提、补例外，必要时改为局部重写。
